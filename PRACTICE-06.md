## Обов'язкова власна реалізація

7. Власні додаткові негативні тести, очищена колекція Postman і звіт.

Моделі, HTTP-адаптер, конфігурація, ізольований приклад і початкові тести
надані. Початкові TODO закономірно не проходять поведінкові перевірки.
Видалення тестів, skip/xfail або сталі відповіді не є виконанням.

## Єдина роль та матриця

| Роль | Дозволено |
|---|---|
| admin | Безпечний список/перегляд користувачів, створення, статус 0/1/2, блокування |
| manager | CRUD курсів; призначення/відрахування викладачів і студентів; читання всіх оцінок |
| teacher | Призначені курси; зарахування студентів на них; створення/читання/зміна лише самостійно виставлених оцінок |
| student | Власні поточні курси; усі власні оцінки, включно з історичними |

Admin НЕ є суперкористувачем. У роботі роль одна; немає ролі — немає
захищеного доступу. Рольове право не замінює перевірку поточного призначення
на курс та автора оцінки. Роль або `teacher_id` не беруться з даних клієнта.
HTTP-призначення ролей та фізичного видалення користувачів немає.

## Дані та міграція

Схема №5 зберігається. Додайте `course_teacher(course_id,teacher_id)` і
`course_student(course_id,student_id)`, складені PK, FK та унікальний індекс
на `user_role.user_id`. Зовнішній ключ не перевіряє прикладну роль.
Кілька наявних ролей або порушення FK — відмова з повним відкатом, не
непомітне видалення даних. Не створюйте зарахування автоматично з grade.

На курсі може бути кілька викладачів. Одна поточна оцінка на студента/курс,
ціле 0..100 — локальна шкала. Чужий автор не перепризначається. За спроби
другої оцінки — 409; чужа оцінка для зміни — 404. Для запису потрібні чинне
призначення викладача і зарахування студента з відповідною роллю.

Відрахування зберігає оцінки. Student читає свої історичні оцінки після
відрахування; teacher після зняття призначення не читає курс. Курс із
оцінками видаляти не можна: 409 без часткового видалення зв'язків.

## JWT і конфігурація

Точний локальний профіль: HS256; `typ=JWT`; issuer `digital-dean-api`;
audience `digital-dean-api:access`; строк 900 секунд; без refresh/logout/
реєстру відкликання. HS256 — MAC за спільним секретом, НЕ шифрування і НЕ
асиметричний цифровий підпис. Ключ JWT не є сіллю парольного хешу.

Обов'язкові поля: `sub,iss,aud,iat,nbf,exp,jti,token_use` і лише вони.
`sub` — канонічний додатний десятковий рядок SQLite-id; iat/nbf/exp — точні
цілі числа UTC; iat=nbf; exp-iat=900; jti — 32 малі шістнадцяткові символи;
token_use=access. Максимум 4096 символів токена. Перевірка MAC і часових
тверджень не вимикається.
Інший алгоритм/тип, параметри заголовка, профіль або пошкодження — відмова.

Секрет `DEAN_JWT_SECRET_HEX` — hex-подання 32..128 випадкових байтів, без стандартного
значення. Bash/Zsh, у тому самому терміналі запуску:

```bash
export DEAN_JWT_SECRET_HEX="$(python -c 'import secrets; print(secrets.token_hex(32))')"
```

PowerShell:

```powershell
$env:DEAN_JWT_SECRET_HEX = python -c "import secrets; print(secrets.token_hex(32))"
```

Не друкуйте й не експортуйте ключ або робочі токени. При заміні ключа
попередні токени не проходять перевірку. Для перевірки перезапуску потрібні
ті самі база та ключ. Тестовий ephemeral-ключ не є production-конфігурацією.

## Контракт активного API

Усі бізнес-шляхи починаються з `/api/v1`; health лишається `/health`.

| Метод і шлях | Успіх | Доступ |
|---|---|---|
| POST /auth/login |200 TokenResponse|Правильний пароль та active; JSON login/password|
| GET /auth/me |200 Me|Кожна з чотирьох ролей|
| GET /users; GET /users/{user_id} |200 UserPublic|admin|
| POST /users |201 UserPublic|admin; status0 стандартно; без автоматичної ролі|
| PATCH /users/{user_id}/status |200 UserPublic|admin; тільки status_id0/1/2|
| PATCH /users/{user_id}/block |200 UserPublic|admin; повтор без побічних змін|
| GET /courses; GET /courses/{course_id} |200|manager усі, teacher/student лише власні поточні|
| POST /courses; PATCH /courses/{course_id} |201/200|manager; поле name|
| DELETE /courses/{course_id} |порожній204|manager; із grade409|
| PUT /courses/{course_id}/teachers/{user_id} |200|manager; точна роль teacher|
| DELETE /courses/{course_id}/teachers/{user_id} |порожній204|manager; grade лишаються|
| PUT /courses/{course_id}/students/{user_id} |200|manager або teacher свого курсу; точна роль student|
| DELETE /courses/{course_id}/students/{user_id} |порожній204|manager; grade лишаються|
| GET /courses/{course_id}/grades |200|manager усі; teacher тільки власне авторство|
| POST /courses/{course_id}/grades |201|teacher; student_id/grade; автор серверний|
| PATCH /courses/{course_id}/grades/{student_id} |200|teacher; тільки поле grade своєї оцінки|
| GET /me/grades |200|student; тільки student_id поточного суб'єкта|

PUT зарахування повторно200 без дубля. DELETE зарахування на наявному курсі
повторно204, навіть якщо зв'язку вже немає. Списки: limit1..100, offset>=0,
порядок за id/студентом/курсом відповідно; фільтр права застосовується ДО пагінації.

`login` більше НЕ повертає bool: `{access_token,token_type:"bearer",expires_in:900}`.
401+`WWW-Authenticate: Bearer` — відсутня/невалідна ідентичність чи inactive/
blocked. 403 — немає потрібної ролі/дозволу. 404 — відсутній або невидимий
ресурс. 409 — конфлікт предметного стану. 422 — очищена невідповідність входу.
500 — контрольований збій бази. Деталі: `authentication required`,
`operation forbidden`, `resource not found`, `operation conflicts with current state`,
`database unavailable`. Не повертайте SQL, input/ctx/body, паролі чи токени.

На кожному запиті читайте поточні роль/статус/зарахування з БД. У записах
повторіть авторизацію в тій самій транзакції, що й зміна. Блокування діє
з наступного запиту, але не відкликає JWT криптографічно: ще чинний токен
може знову працювати після розблокування. Роль у токен не записується.

## Початкові записи і перевірки

Після TODO реалізації й завершеної ініціалізації №5:

```bash
python -m app.practice06.migration
python -m app.practice06.migration
python -m app.practice06.bootstrap create --login lab_admin --role admin \
  --name "Lab admin" --email lab.admin@example.com
```

Пароль вводиться через getpass. Аналогічно створіть `lab_manager`,
`lab_teacher_a`, `lab_teacher_b`, `lab_student_a`, `lab_student_b` з їхніми
ролями та різними синтетичними email. Для Postman використовуйте спільний
одноразовий навчальний `lab_password`, заданий ЛИШЕ у локальному середовищі
Postman. Жодного стандартного адміністратора програма не створює.

```bash
python -m pytest tests/test_practice06_tokens.py tests/test_practice06_migration.py tests/test_practice06_access.py
python -m uvicorn app.main:app --host 127.0.0.1 --reload
```

Надані тести використовують незалежні копії тимчасової синтетичної бази.
Додайте власні перевірки збою/rollback, спроб SQL-ін'єкції, підміни автора,
зміни стану між залежністю й транзакцією, відсутності обхідних маршрутів та
перезапуску. Зберігайте попередні перевірки внутрішньої логіки, а навмисно
змінені HTTP-контракти оновіть; не повертайте незахищені маршрути заради тестів.

Імпортуйте `postman/digital-dean-practice-06.postman_collection.json`.
Колекція приймає тільки `http://127.0.0.1:8000`, отримує id і токени з
відповідей, створює новий курс для кожного запуску. Курс із оцінкою лишається
як доказ: колекція не видаляє оцінок для обходу409. Наприкінці змінні токенів
очищуються, але це не серверне відкликання. Перед експортом перевірте, що
колекція та середовище не містять пароля або токенів.
