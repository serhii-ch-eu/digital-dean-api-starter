## Що реалізувати

1. `audit.py`: тригери й атомарна повторювана міграція.
2. `filelog.py`: форматування дозволених полів і надійне передавання подій.
3. `middleware.py`: незалежний контекст запиту, серверний `X-Request-ID`,
   тривалість і контрольовані події завершення/відмов.
4. `integration.py`: підключення до ТОГО САМОГО застосунку після №6,
   збереження життєвого циклу й відмова запуску без працездатного журналу.
5. `inspect.py`: локальний параметризований перегляд історії лише для читання.
6. Власний маршрутизатор №6: `verified_access_context`, поточний principal,
   `bind_identity`; успішний парольний вхід — `bind_login`, події входу/видачі.
7. Власний сервіс №6: запис оцінок через `open_audited_database` із
   `audit_for_actor(actor_id)`, повторна авторизація всередині транзакції.
8. Події перегляду оцінок і підтверджених предметних операцій, додаткові тести
   та звіт. Надані `NotImplementedError` мають бути замінені власною логікою.

Каркас не підмінює `app/main.py` або завершений сервіс. Самостійно змініть
потрібні місця у власних файлах №6. Не вмикайте старі незахищені маршрути.

## Аудит бази

Таблиця `grade_audit`: `id`, `actor_id`, `occurred_at`, `operation`,
`request_id`, `old_values`, `new_values`. Знімки — JSON із **точно чотирма**
полями `student_id`, `teacher_id`, `course_id`, `grade`; відсутній знімок — SQL NULL.
Для INSERT старий стан NULL, для DELETE новий NULL, для UPDATE наявні обидва.
Жодного дублювання парольних або інших таблиць у знімках.

Три AFTER-тригери на `grade` та два захисні BEFORE-тригери на `grade_audit`:
імена наведено в `audit.TRIGGER_NAMES`. UPDATE порівнює ВСІ чотири поля
через `IS NOT`; фактично незмінний рядок не утворює історії.
Виконавець — чинний активний запис `user` із довіреного контексту з'єднання,
не `teacher_id` оцінки й не значення клієнтського JSON. Функції контексту та
JSON-знімків надані й не потребують необов'язкових JSON-розширень SQLite.

Зміна й історія — одна транзакція. Збій аудиту скасовує зміну. Міграція не
видаляє наявних даних, не вигадує минулих подій і перевіряє свою схему при
повторному виконанні. Історія не має каскадних посилань, які стерли б докази
разом з оцінкою чи обліковим записом. UPDATE/DELETE історії заборонені
захисними тригерами. Довірений власник файлу/схеми все ще може змінити БД:
це не криптографічна незмінність і не доказ невідмовності авторства.

DELETE оцінки досліджується тільки локально на тимчасовій синтетичній базі.
**Новий маршрут видалення оцінки не додається.** Не застосовуйте REPLACE.

## Файлові події

`var/logs/security.jsonl`, UTF-8, один JSON-об'єкт на рядок; `Event` —
дозвільний список полів. Назви й рівні — `events.EVENT_LEVELS`.

| Подія | Коли записувати |
|---|---|
| app.started / app.stopped | Успішний запуск / штатне завершення життєвого циклу |
| http.completed / http.failed | Завершення запиту / серверний збій |
| auth.login_succeeded / auth.login_failed | Успішний активний парольний вхід / відмова |
| auth.token_issued / auth.token_rejected | Видача / відмова прийняти токен, без його вмісту |
| access.denied / input.rejected | Відмова 403 або невидимий/відсутній ресурс 404 / помилка 422 |
| grade.read | Успішне читання оцінок: курс за наявності та кількість, НЕ значення |
| grade.created / grade.updated / grade.unchanged | Після COMMIT; створення / фактична зміна / повтор того самого значення |
| operation.succeeded / operation.failed | Керування користувачами, курсами, зарахуваннями або відхилена предметна дія |
| database.failed | Контрольований збій БД без SQL, шляхів і тексту винятку |

Поля `action`, `course_id`, `student_id`, `target_id`, `returned_count`
заповнюються лише з перевірених сервером значень. `committed=true` у подіях
створення/зміни оцінки означає вже підтверджену транзакцію. Не називайте
відкочену чи заборонену операцію успішною. Не дублюйте один вид події для
одного запиту в middleware і в маршрутизаторі.

Для дій над користувачем записуйте target_id, для зарахування — також
course_id. Статуси 0/1/2 відрізняйте серверними action `user.deactivate`,
`user.activate`, `user.block`. Невдалий предметний запис із 409 має
operation.failed, а не подію підтвердженої зміни.

## Ідентичність і конфіденційність

`request_id` — новий UUID4 сервера для КОЖНОГО HTTP-запиту, той самий у
файлі, аудиті БД і заголовку `X-Request-ID` відповіді. Вхідний однойменний
заголовок його не замінює. `session_ref` — SHA-256 від випадкового `jti`
лише після повної перевірки профілю №6. Це кореляція використання токена,
не TCP-сеанс і не окрема серверна сесія. Logout/refresh не додаються.

Не записуйте JWT, вихідний jti, Authorization, пароль, хеш, сіль, ключ,
тіло запиту/відповіді, query string, довільний шлях клієнта чи трасування
винятку. Невалідний токен не є джерелом actor_id/ролі. Подія успішного
входу може мати role=null, оскільки правильний активний вхід без призначеної
ролі не дає захищених повноважень. Шаблон маршруту береться із сервера,
невідомий маршрут позначається `<unmatched>`.

UTC — час машини сервера, не довірена зовнішня позначка; порядок історії —
за id, тривалість — монотонним таймером. Не використовуйте глобального
«останнього користувача», спільне SQLite-з'єднання чи неперевірені атрибути.

## Межі надійності

Локальний стенд `127.0.0.1`, один процес запису, один worker. Ротація
приблизно за 1 МіБ, три резервні файли — навчальний профіль; повна історія
файлу при ротації не гарантується. Для тестів задавайте менший поріг.
Не використовуйте цей обробник як багатопроцесний збирач журналів.

Неможливість початкового запису журналу зупиняє запуск. Runtime-збій
файлового запису позначається фіксованим безпечним повідомленням у stderr
та False від sink.emit; жодних токенів або тексту винятку. Якщо COMMIT вже
виконано, збережіть правдиву успішну відповідь, не повідомляйте про відкат.
SQLite та JSONL не є однією атомарною транзакцією. Це не розподілений
exactly-once журнал. Доступ до сховищ обмежте засобами власної ОС.


Збережіть локальну конфігурацію JWT №6. Приклад підключення у власному main:

Стандартний access log сервера вимкнено: власний журнал записує шаблон
маршруту, а не клієнтський шлях і query string. Інші підключені обробники
також перевірте на відсутність облікових даних і тіл повідомлень.

```python
from app.practice07.integration import install_practice07

# Після наявного install_practice06(app), без створення другого app:

```

Тести працюють із tmp_path, а не з робочим сховищем. Ініціалізацію
синтетичного шаблону №6 виконуйте ДО встановлення тригерів, потім копіюйте
його для незалежних сценаріїв. Оновіть регресійні фікстури до міграції №7;
не використовуйте skip/xfail та не вимикайте аудит для проходження перевірок.

## Postman та локальна інспекція

Імпортуйте `postman/digital-dean-practice-07.postman_collection.json`.
Зберігайте лише локально одноразовий `lab_password` і використовуйте шість
синтетичних записів №6. Колекція отримує id/token з відповідей, перевіряє
X-Request-ID та зберігає audit_create_request_id/audit_update_request_id
для зіставлення. Вона не читає файлів сервера чи SQLite через HTTP.

```bash
python -m app.practice07.inspect --limit 20
```

Для пошуку конкретного запису додайте `--request-id` із фактичним UUID
відповіді. Перегляд тільки локальний і лише для читання; manager/teacher/
student/admin не отримують нових HTTP-прав на журнали. Перед експортом
видаліть пароль і токени зі змінних колекції/середовища. Журнали, бази й
дампи не публікуйте; до звіту додайте лише мінімальні синтетичні витяги.
